# Interface Contracts — V01

## Application customer surface

Proposed versioned HTTP routes. Authenticate the seeded customer identity, derive customer ID server-side and apply ownership to every read and replay.

| Interface | Request and result |
| --- | --- |
| `POST /api/v1/wallet/top-ups` | Positive integer `amountIrr`, customer-scoped `Idempotency-Key`. Return 202 with stable `topUpId` and status location after durable admission. Exact replay returns the same acknowledgement; a changed amount conflicts (409). Known ineligibility is rejected. An authorization rejection discovered after admission is visible as failed initiation, with no session or journal. |
| `GET /api/v1/wallet/top-ups/{topUpId}` | Return owned status, amount, customer-safe message code, and session continuation when ready and applicable. Return 404 for an absent or foreign reference. Reads are side-effect free; scheduled work performs inquiry independently of reads. |
| `GET /api/v1/wallet/balance` | Return committed `availableIrr` from Ledger for the authenticated customer. If Ledger is unavailable, return a retryable unavailable result rather than a fabricated zero. |
| `POST /api/v1/payments/mock/callback` | Authenticate the synthetic provider; use a scoped payment reference as a notification only. Accept valid notices regardless of age and acknowledge after recording or coalescing durable inquiry work. Do not disclose the customer's data or apply financial effects here. |

Customer status separates initiation, waiting for provider, definitive payment failure, verified payment awaiting Ledger, successful posting, and posting exception. Success exposes the credited bucket or equivalent message; a restricted credit reports that the money was recorded and cannot be spent. An unverified issuer return is communicated as completed only on matched definitive provider evidence. The 72-hour scenario attributes the return to the issuing bank.

## Synthetic gateway boundary

Create or look up a session under the original stable request reference and return provider payment ID, creation time and continuation. Verify/inquire server-to-server under the original scoped payment identity. Definitive capture includes payment ID, capture reference and amount. Definitive expiry and issuer return must bind to that payment; timeout, unmatched evidence and ambiguous replies remain unresolved. The C01 deadline applies only to first verification. Inquiry can return an already verified capture after the window without an original verification timestamp. [Specification](../spec.md)

## Application → Ledger

Use the existing versioned [Financial Operations contract](../../../docs/FINANCIAL_OPERATIONS.md#3-transport-and-envelope). Derive ProducerId from scoped service credentials. Authorize operation types and lookup scope. Credentials and internal endpoints are unavailable to customer and callback callers.

- `POST /internal/v1/control-commands` and `GET /internal/v1/control-commands/{commandId}` — C04 AuthorizeTopUpInitiation with customerId, paymentIntentId and stable commandId. Open the gateway session only after Applied.
- `POST /internal/v1/operations` — F02 ApplyGatewayPaymentEvidence in the common envelope, with paymentId, captureRef, capturedIrr, stable evidenceBatchId, integrity-bound evidenceRef and empty confirmedReversals for V01. Unsupported operation types fail without execution.
- `GET /internal/v1/operations/{operationId}` — read the immutable decision under producer scope. Posted includes the journal reference, decision time and credited bucket in the typed decision detail. Exact replay preserves the result. A changed canonical payload conflicts. A duplicate capture under a different operation ID cannot post again. Timeout, unavailable and ordinary NotFound do not establish rejection.
- `GET /internal/v1/customers/{customerId}/balances` — read the authoritative projection using authorized Application delegation. Return the current balance independently of any cached top-up status.
