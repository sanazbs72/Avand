# Interface Contracts — V03

This contract specializes [Financial Operations F05](../../../docs/FINANCIAL_OPERATIONS.md#f05-sellgold) for the clarified [V03 spec](../spec.md). The customer may enter a weight or a gross IRR target. Limits apply to gross, fee rounds up, and acceptance requires free liquidity ≥ net. The [V01](../../001-fund-irr-wallet/contracts/v01.md) and [V02](../../002-buy-gold-wallet/contracts/v02.md) contracts are preserved.

## Customer surface

Customer identity comes from authenticated credentials only. A missing or foreign reference returns the same not-found response. Reads trigger no financial work.

| Interface | Request and response |
| --- | --- |
| `POST /api/v1/gold/sell-quotes` | Body has exactly one of positive whole `quantityMg` or positive whole `requestedGrossIrr`. Returns 201 with quote ID, input mode, sell price per gram, weight mg, gross IRR, fee rate and amount, net IRR, and UTC issue and expiry. Out-of-bounds gross, weight < 1 mg or net ≤ 0 returns a safe validation reason. A missing or stale price returns a retryable unavailability reason. Issuance reserves no gold or liquidity. It may show a known shortfall of the customer's own available gold, and it never discloses platform liquidity. |
| `POST /api/v1/gold/sell-orders` | Body has only `quoteId`, plus an `Idempotency-Key` header. Returns 202 with order ID and status location after durable admission. An exact retry returns the same acknowledgement, even after expiry. The same key with another quote, or another key for a claimed quote, returns 409 with no second order. |
| `GET /api/v1/gold/sell-orders/{orderId}` | Returns the owned order with exact authorized amounts, status `Processing`, `FinancialOutcomeUnknown`, `Completed` or `Rejected`, and a safe reason. `InsufficientLiquidity` is shown as "sales temporarily unavailable". An expired rejection offers a refresh with the original input mode and value, which needs a new quote and new confirmation. |
| `GET /api/v1/gold/balances` | Unchanged from V02. After a completed sale, `availableIrr` includes the net and `availableGoldMg` excludes the sold weight. |

## Application → Ledger

Uses the existing `Application.Trading` credential and the shared internal route. Payments can't send `SellGold`.

| Interface | Request and response |
| --- | --- |
| `POST /internal/v1/operations` | Envelope `operationType=SellGold`, stable operation ID, envelope customer ID, business reference `GoldSellOrder` / order ID / `Execute`, customer actor. Payload `quoteSnapshot`: side `Sell`, quote ID, UTC issue and expiry, `bidIrrPerGram`, `quantityMg`, `grossIrr`, `feeRatePpm`, `feeIrr`, `netCreditIrr`, `policyVersion`. Ledger recomputes gross, fee and net from weight, bid and rate. |
| `GET /internal/v1/operations/{operationId}` | Returns the stored sell result under producer scope. Posted: journal reference and decision time. Rejected: decision time, stable reason, no journal. Replay is identical. |

Rejection reasons: `DuplicateBusinessAction`, `QuoteAlreadyUsed`, `UnsupportedQuotePolicy`, `QuoteTermsInvalid`, `QuoteExpired`, `CustomerNotEligible`, `OrderOutOfBounds`, `InsufficientGold`, `InsufficientLiquidity`. The response semantics stay as in V02: 200 Posted or Rejected, 409 on a payload conflict under the same ID, 400 on a malformed envelope. A timeout or ordinary 404 leaves the outcome unknown. Recovery resends the same identity and frozen request.
